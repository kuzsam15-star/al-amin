# Почтовая инфраструктура AL-AMIN

Последняя сквозная проверка: 2 августа 2026 года. Этот документ не содержит и не должен содержать пароли, API-ключи, SMTP-пароли, токены подтверждения или иные секреты.

## Назначение и сервисы

- **Supabase Auth** создаёт аккаунты, отправляет письма подтверждения и восстановления доступа.
- **UniSender Go** — транзакционный почтовый провайдер.
  - Supabase Auth использует его через Custom SMTP.
  - Серверные уведомления приложения используют UniSender Go Web API через `src/lib/email/provider.ts`.
- **DNS `ailvi.ru`** подтверждает домен отправителя, SPF/DKIM и домен ссылок.
- **Next.js** принимает возврат из письма в `/auth/callback` и сохраняет сессию в cookie.

## Несекретные настройки

| Параметр | Значение |
| --- | --- |
| SMTP host | `smtp.go2.unisender.ru` |
| SMTP port | `587` |
| Шифрование | TLS / STARTTLS |
| SMTP username | Идентификатор аккаунта UniSender Go; не хранить в репозитории, если он используется вместе с секретом |
| Отправитель Supabase Auth | `AL-AMIN <no-reply@ailvi.ru>` |
| Домен отправителя | `ailvi.ru` |
| Домен ссылок | `alamin.ailvi.ru` |
| Провайдер серверных писем | `EMAIL_PROVIDER=unisender-go` |
| Web API endpoint | `https://goapi.unisender.ru/ru/transactional/api/v1/email/send.json` |

Пароль SMTP и `UNISENDER_GO_API_KEY` хранятся только в защищённых настройках соответствующего сервиса или в серверных переменных окружения. Они никогда не попадают в `NEXT_PUBLIC_*`, исходный код, Git или документацию.

## DNS-аутентификация

| Запись | Действие | Назначение |
| --- | --- | --- |
| `ailvi.ru` TXT SPF | Изменена существующая единственная SPF-запись | Разрешает UniSender Go отправлять письма от домена, сохраняя действующие механизмы хостинга. Итог: `v=spf1 ip4:31.31.198.35 a mx include:_spf.hosting.reg.ru include:spf.unisender.ru ~all` |
| `ailvi.ru` TXT `unisender-go-validate-hash=…` | Добавлена | Подтверждает владение доменом для UniSender Go. Значение проверяется по фактической записи в DNS, а не берётся из примера документации. |
| DKIM для `ailvi.ru` | Добавлена по значениям из кабинета UniSender Go | Криптографически подтверждает письма. Selector и значение определяются UniSender Go и не дублируются в коде проекта. Статус домена/DKIM в кабинете должен быть «Настроен» / подтверждён. |
| `alamin.ailvi.ru` | Добавлено делегирование DNS домена ссылок по значениям UniSender Go | Позволяет сервису безопасно обрабатывать ссылки в письмах. Не заменяет MX, A/AAAA, CNAME или почтовые записи основного домена. |

SPF-правило должно оставаться единственным TXT SPF для `ailvi.ru`. При смене провайдера нельзя удалять действующие механизмы `ip4`, `a`, `mx` и `include:_spf.hosting.reg.ru` без отдельной проверки.

## Что вызвало первоначальные ошибки

1. Регистрация доходила до Supabase Auth и SMTP, но UniSender Go отклонял письмо до создания пользователя.
2. Первая причина: не был настроен домен ссылок. SMTP возвращал `550 5.7.1 Sender address rejected: Denied: custom tracking domain required for sending`.
3. После настройки домена ссылок проявилось второе ограничение бесплатного тарифа: `553 5.1.10 No valid recipients` — отправка была разрешена только на подтверждённые адреса и домены, поэтому Gmail блокировался.
4. После перехода на платный тариф UniSender Go оба ограничения сняты: подтверждение регистрации ушло на внешний Gmail, ссылка завершила регистрацию и сессия сохранилась.

Это были проблемы почтовой инфраструктуры и тарифных ограничений, а не ошибка пароля, формы регистрации или Google OAuth.

## Текущий статус

- Custom SMTP в Supabase Auth включён.
- Подтверждение email включено.
- Домен `ailvi.ru`, SPF, DKIM и `alamin.ailvi.ru` настроены для UniSender Go.
- Платный тариф UniSender Go разрешает транзакционные письма на внешние адреса.
- Сквозная регистрация с новым внешним Gmail прошла успешно.

## Проверенный сценарий

1. На `http://localhost:3000/register` создан новый пользователь с email и паролем.
2. Supabase Auth зарегистрировал успешный `POST /signup` со статусом `200`; пользователь появился в списке Auth Users.
3. В Gmail пришло письмо `Confirm your email address` от `AL-AMIN <no-reply@ailvi.ru>`.
4. Ссылка из письма прошла через `alamin.ailvi.ru`, Supabase `/verify` и локальный `/auth/callback`.
5. Открылся `/apply` с активной сессией, затем `/cabinet`.
6. После выхода повторный вход по тому же email и паролю открыл кабинет; обновление страницы сохранило сессию.

## Диагностика будущих проблем

Проверять в следующем порядке, не меняя DNS или Auth-настройки наугад:

1. В форме регистрации зафиксировать время и тестовый адрес (использовать доступный, новый адрес).
2. В Supabase Dashboard → **Logs** отфильтровать `Auth` и найти `POST /signup`.
   - `200` означает, что Auth принял регистрацию.
   - `5xx` с SMTP-текстом означает, что проблема после Auth, на стороне почтового транспорта.
3. В Supabase Dashboard → **Authentication → Users** проверить появление пользователя.
4. В UniSender Go открыть журнал отправки и сверить время, получателя и причину отказа, если она есть.
5. Проверить письмо во «Входящих» и в «Спаме». Для ссылки подтвердить цепочку: домен ссылок → Supabase `/verify` → `/auth/callback` → целевая страница.
6. Проверить DNS из независимого резолвера:
   - один и только один SPF TXT для `ailvi.ru`;
   - наличие `include:spf.unisender.ru`;
   - запись валидации домена;
   - статус DKIM и домена ссылок в UniSender Go.
7. Если письмо не создаёт сессию, проверить разрешённые Redirect URLs Supabase и `NEXT_PUBLIC_SITE_URL`; не менять SMTP без доказательств ошибки в журнале.

## Правила безопасного сопровождения

- Не создавать вторую SPF-запись.
- Не менять MX, A/AAAA или существующие записи почты/сайта ради отправки транзакционных писем, если UniSender Go явно этого не требует.
- При обновлении DNS сначала сохранить текущий снимок зоны и дождаться распространения записей.
- Не публиковать секреты в чате, `.env.example`, логах или Git.
- Для production использовать HTTPS-домен и добавить точный callback URL в Supabase Auth; `localhost` оставлять только для локальной разработки.
