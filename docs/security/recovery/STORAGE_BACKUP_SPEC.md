# AL-AMIN Storage Backup and Restore Specification

## 1. Purpose and selected mechanism

Database backup does not protect Storage object bytes. AL-AMIN therefore needs a
separate encrypted backup of `avatars` and `profile-media` plus database-backed
policy recovery and explicit bucket configuration recovery.

The preferred supported mechanism is an owner-operated S3-compatible client
against the official Supabase Storage S3 endpoint. The alternative is the
official Supabase Storage download tooling. The S3 protocol must be enabled and
temporary credentials generated by the owner. Credentials are never provided to
Codex. Supabase S3 object versioning is not supported, so an external immutable
generation is mandatory.

## 2. Owner-operated wrapper contract

The reviewed owner-operated wrapper is implemented under `scripts/recovery`.
It meets these requirements before it receives credentials:

- dry-run is the default; `--capture` and `--restore` are explicit and mutually
  exclusive;
- source and target endpoints are explicit, unequal, and shown only as redacted
  aliases;
- source access is read/list only; the implementation contains no source delete,
  update, move, or upload path;
- credentials are accepted only from ephemeral process environment or an
  approved secret manager and are never printed;
- output must be outside the repository in a pre-created owner-approved folder;
- each generation is encrypted and authenticated; the key is stored separately;
- full object paths are encrypted in the artifact and represented in evidence by
  a salted SHA-256 path hash only;
- object bytes are never logged; evidence retains content hash, size, MIME class,
  and bucket aggregate only;
- checkpoint state is encrypted and permits resume without duplicate writes;
- target writes use no-overwrite semantics; an existing target object is accepted
  only after its content hash matches;
- no source deletion exists, and target cleanup is a separately approved action;
- failures close the run and preserve the prior verified generation.

The wrapper passed synthetic local regression and the dated production-derived
read-only export with two isolated restores. Credential issuance and artifact
location remain owner decisions for every future generation.

## 3. Capture manifest

For each encrypted generation, retain outside Git:

- generation ID and UTC timestamp;
- bucket alias;
- salted path hash;
- byte length;
- SHA-256 of plaintext content inside the encrypted manifest;
- ciphertext SHA-256 for transport verification;
- normalized MIME class;
- capture status and retry/checkpoint state.

Committed evidence may contain only per-bucket object count, total bytes, MIME
distribution, aggregate Merkle/root hash or deterministic manifest hash, and
missing/corrupt counts. Filenames, user IDs, UUIDs, full paths, bytes, and media
content are forbidden in repository evidence.

## 4. Bucket configuration contract

| Bucket | Visibility | Size limit | Live MIME allowlist | Recovery note |
| --- | --- | ---: | --- | --- |
| `avatars` | Public | 2 MiB | JPEG, PNG, WebP | Public-read behavior must be revalidated |
| `profile-media` | Private | 5 MiB | JPEG, PNG, WebP | Live MIME state is broader than the latest tracked historical assignment |

Seven application policies on `storage.objects` are expected from the database
catalog evidence. Policies and grants are restored/reconciled through the
database path, not by copying object bytes.

## 5. Capture procedure

1. Owner creates time-limited source credentials with the narrowest supported
   list/read scope and records their expiry outside Git.
2. Operator runs dry-run inventory and reviews bucket aliases and aggregate-only
   estimates.
3. Operator captures objects into a new encrypted generation; no source mutation
   is possible.
4. Wrapper verifies every ciphertext and content hash, then writes the signed or
   authenticated generation summary.
5. Plaintext temporary files are securely removed; encrypted artifact and key
   remain in separate custody.
6. Temporary source credentials are revoked.

If the platform cannot issue bucket-scoped read credentials, the owner must
explicitly approve the broader credential for a short-lived local process. It is
never sent to Codex and is revoked immediately after capture.

## 6. Isolated restore procedure

1. Create fresh `avatars` and `profile-media` buckets in a new isolated target
   with the manifest settings.
2. Supply a target-only write credential from process environment.
3. Decrypt one object at a time in memory or a protected temporary location.
4. Verify plaintext hash before upload and upload with no-overwrite semantics.
5. Verify target bytes/hash after upload; checkpoint only after verification.
6. Reconcile per-bucket counts, total bytes, MIME distribution, and aggregate
   hash.
7. Apply/reconcile Storage policies via the database recovery path.
8. Run synthetic public/private access checks without displaying real objects.

PASS requires source artifact and target to have identical counts, bytes, and
content hashes, with zero missing, corrupt, duplicate-conflict, or unexpected
objects.

## 7. SEC-001 and deletion safety

Canonical media and legacy submission sources are both retained during SEC-001
deployment and recovery. A rollback or restore never deletes canonical media.
Old submission source is not deleted until canonical coverage, database
references, object hashes, and a later retention/GC policy are independently
verified. Partial backfill resumes from checkpoint and does not overwrite an
existing canonical object.

## 8. Current proof status

- Source object inventory: READ under owner-approved read-only access.
- Encrypted backup artifact: CREATED outside Git; authenticated and hash-checked.
- Isolated targets: two fresh loopback-only disposable Supabase projects.
- Restore: PASS twice.
- Object count: 36 in each restore.
- Per-object content-hash reconciliation: PASS twice.
- Source mutations: none; operations were restricted to `LIST`/`HEAD`/`GET`.
- Temporary S3 key: owner-confirmed deleted before encryption.
- Residual plaintext or disposable resources: zero.
