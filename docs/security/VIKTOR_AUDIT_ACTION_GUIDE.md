# AL-AMIN Audit Action Guide for Viktor

## 1. Что мы сейчас делаем

Мы готовим очень короткий и ограниченный технический доступ, чтобы увидеть **карту устройства базы данных** AL-AMIN: названия таблиц, правила доступа, настройки безопасности и связи между объектами. Такая карта нужна, чтобы позже безопасно собрать чистую тестовую копию структуры базы без реальных данных.

Этот шаг **не меняет сайт**, не меняет пользователей, заявки, отзывы, файлы, настройки входа или правила доступа для посетителей. Он не исправляет уязвимости и не создаёт новую базу.

Временный доступ нужен только на время одной проверки. После проверки он должен быть удалён.

## 2. Что Виктор НЕ делает

Виктор не должен:

- передавать `service_role`, пароль базы, API key, token, JWT или любой секрет в чат, Git, файл проекта или кому-либо ещё;
- экспортировать пользователей, заявки, отзывы, жалобы, файлы, логи или таблицы;
- открывать и копировать страницы с пользователями, ключами, секретами, файлами или данными таблиц;
- менять сайт, миграции, настройки входа, Storage, RLS, policies, роли пользователей или настройки Supabase;
- запускать случайный SQL, команды из интернета, `supabase login`, `supabase link`, dump, migration или скрипт, который не был отдельно проверен;
- использовать существующий постоянный аккаунт приложения вместо временного технического доступа.

Если кто-то просит сделать что-либо из этого списка, нужно остановиться.

## 3. Первый шаг

1. Открой локальную папку проекта AL-AMIN и убедись, что в ней нет незакоммиченных изменений, кроме явно согласованных documentation-only файлов.
2. Открой документы `AUDIT_EXECUTION_PACKAGE.md` и `AUDIT_IDENTITY_RUNBOOK.md`. Они объясняют границы будущей проверки.
3. В обычном браузере открой Supabase Dashboard только под своим существующим владельческим аккаунтом.
4. Перед любым действием внимательно проверь название и адрес проекта: это должен быть именно AL-AMIN production project, а не другой проект или тестовая среда.
5. Пока не открывай SQL Editor и ничего не запускай. Следующий guided step должен содержать отдельное человеческое подтверждение exact one-off setup/cleanup package.

Если название проекта непонятно, страница выглядит неожиданно или есть сомнение, закрой страницу и остановись. Не угадывай.

## 4. Создание временного доступа

Позже будет создан один временный технический аккаунт. Он нужен только для чтения карты устройства базы, а не её содержимого.

Почему это безопаснее обычного административного доступа:

- он должен работать только ограниченное время;
- он не должен видеть реальные строки, пользователей или загруженные файлы;
- он не должен уметь что-либо менять;
- его пароль хранит только Виктор в своём password manager;
- после проверки аккаунт удаляется полностью.

Виктор создаёт этот доступ только после отдельного подтверждения точного setup script. Не придумывай имя, срок, пароль или SQL самостоятельно. Не вставляй пример из документации и не меняй существующие аккаунты.

## 5. Запуск аудита

После того как временный доступ создан и проверен, Виктор вручную запускает заранее проверенную программу аудита на своём компьютере.

Что ожидать:

- программа создаст один файл с технической картой базы и один короткий понятный отчёт;
- в отчёте будут названия объектов и правила доступа, но не содержимое таблиц;
- до передачи результата нужно проверить, что в файлах нет людей, email, файлов, паролей, ключей или токенов.

Где сохранить результат:

- сначала в отдельную временную папку вне проекта и вне синхронизируемых папок;
- после проверки оставить только очищенные (redacted) файлы и короткую отметку, что временный доступ был удалён;
- не сохранять raw output, screenshots с данными, credential или connection string в Git.

Если заранее проверенной программы, её имени, контрольной суммы или понятной команды нет, не запускай ничего. Остановись и запроси следующий guided step.

## 6. Проверка результата

Безопасный результат содержит только технические сведения:

- названия таблиц и их полей;
- названия правил доступа;
- названия функций, views и triggers;
- настройки bucket'ов без списка файлов;
- сведения о включённых способах входа без списка пользователей.

В результате **не должно быть**:

- имен, email, телефонов, ID пользователей, текста заявок или отзывов;
- строк таблиц, списков файлов, файлов Storage или логов;
- паролей, ключей, token, JWT, connection strings или других секретов.

Если найден хотя бы один такой элемент, не отправляй файл дальше. Закрой аудит, сохрани только минимальную заметку без данных и сообщи, что произошла остановка по безопасности.

## 7. Удаление доступа

Сразу после проверки:

1. Закрой программу аудита.
2. Выполни только заранее проверенную часть cleanup package: она отключает временный доступ и удаляет именно временный аккаунт.
3. Проверь, что этим временным аккаунтом больше нельзя подключиться.
4. Удали его пароль из password manager только после подтверждения, что аккаунт удалён.
5. Сохрани только очищенный отчёт и короткую отметку об удалении доступа.

Не удаляй другие аккаунты, не меняй существующие permissions и не пытайся самостоятельно исправить ошибку.

## 8. Если что-то пошло не так

Немедленно остановись, если:

- попросили пароль, ключ, `service_role` или token;
- Dashboard показывает данные пользователей, файлов или секретов;
- временный аккаунт получил право читать данные или что-то менять;
- выбран не тот проект;
- output содержит данные людей или секреты;
- неясно, что именно нужно нажать или вставить.

В такой ситуации ничего не исправляй самостоятельно. Закрой текущую страницу/программу, не передавай чувствительный output, и сообщи: **«Аудит остановлен: требуется безопасная проверка»**. Если временный доступ уже был создан, выполни только заранее проверенное удаление этого временного доступа.
