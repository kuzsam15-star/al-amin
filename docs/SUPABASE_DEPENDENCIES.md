# Зависимости от Supabase

## Используется сейчас

| Область | Использование | При переносе |
|---|---|---|
| Auth | Google OAuth, magic-link, пароль, сессии и `auth.users` | Заменить Auth-провайдером с OIDC/OAuth и email-ссылками |
| PostgreSQL | таблицы, миграции, триггеры, представления, RPC | Переносится в обычный PostgreSQL |
| RLS | доступ владельца, модератора, администратора | Воспроизвести через PostgreSQL claims/RLS или серверный API |
| Storage | `profile-media`, объекты и политики | Заменить S3-совместимым объектным Storage |
| Клиенты | `@supabase/ssr`, `@supabase/supabase-js` | Заменить адаптерами Auth, DB и Storage |

## Переносимо без смены бизнес-правил

- Next.js-интерфейс и маршруты;
- структура заявок, профилей, ревизий и модерации;
- статусы, роли, аудит, отзывы и значки доверия;
- SQL-ограничения, триггеры и публичные представления с небольшой адаптацией;
- формат путей медиа и controlled media-route.

## Что заменить в первую очередь

1. `auth.uid()` и связь с `auth.users`.
2. RLS-политики Supabase и claims ролей.
3. `storage.objects` / `storage.buckets` и выдачу файлов.
4. Прямые вызовы Supabase из UI и server actions — вынести за адаптеры данных.
5. Конфигурацию OAuth и отправку auth-писем.

## Практический план переноса

1. Зафиксировать миграции и экспорт PostgreSQL-схемы.
2. Выбрать российский PostgreSQL, Auth и S3-совместимый Storage.
3. Реализовать адаптеры без изменения экранов и бизнес-процессов.
4. Перенести тестовую копию данных и медиа.
5. Проверить роли, ревизии, публикацию, изображения и OAuth.
6. Переключать production только после параллельной проверки.
